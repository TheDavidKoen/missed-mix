# Architecture

How the pieces fit, and where the boundaries are. Decisions and their rationale
live in [`adr/`](adr); this file describes the shape that resulted.

## Request path

Everything is one Cloudflare Pages project. There is no separate API server, and
no origin behind the edge.

```text
browser
  │
  ▼
Cloudflare Pages  ──▶  _worker.js/index.js        the edge entry
                          │
                          ├─ GET/HEAD ─▶ env.ASSETS  static files, hashed, immutable
                          │
                          └─ otherwise ─▶ React Router request handler
                                              │
                                              ├─ loaders   read
                                              └─ actions   write
```

Pages advanced mode hands **every** request to `_worker.js` and serves no static
file on its own, so the entry does the asset lookup itself. Three things in it
are load-bearing and are asserted by `pnpm run budget`:

- The asset lookup is **GET and HEAD only**. A `POST` whose path happened to match
  an asset would otherwise be answered with the asset and never reach an action.
- Requests under `/_worker.js/` are refused. The asset binding is backed by the
  output directory, which contains the compiled server bundle.
- Security response headers are set here rather than in a `_headers` file, because
  `_headers` applies only to static responses and SSR responses would miss them.

The entry is generated by [`scripts/bundle-pages.mjs`](../scripts/bundle-pages.mjs)
because React Router 8 ships no Pages adapter. See
[ADR 0002](adr/0002-cloudflare-pages-over-workers.md).

## Layers

| Layer | Lives in | Rule |
|---|---|---|
| Route modules | `app/routes/` | One file per URL. Loader, action, component. Thin. |
| Boundary logic | `app/lib/` | Schemas and the work an action delegates to. No JSX. |
| Components | `app/components/` | Presentation. No data access, no validation. |
| Copy | `app/content.ts` | Every user-facing string. |
| Tokens | `app/app.css` | Colour, type, radius, easing, under `@theme`. |

Route modules stay thin on purpose. `app/routes/login.tsx` is fifteen lines: its
action calls `beginSignIn` and its component renders `AuthPanel`. When stage 2
replaces the `501` with a real OAuth redirect, one function in `app/lib/auth.ts`
changes and both routes follow.

`login.tsx` and `register.tsx` are deliberately near-identical rather than merged.
They differ in copy today and will differ in where a first-time account lands
after the callback. Two thin files that diverge cleanly beat one file with a
branch in it.

## Validation

Every value that arrives from outside is untrusted until a Zod schema has parsed
it. That includes form fields, query strings, cookies and third-party API
responses.

Schemas live in `app/lib/` so one definition serves the form, the action and,
from stage 3, the database layer. `providerSchema` is both the allowlist an
action validates against and the list the UI iterates to render buttons, so a
provider cannot appear in the interface without being accepted by the server, or
the reverse.

## Identity and data

No passwords exist anywhere in the system ([ADR 0004](adr/0004-oauth-only-identity.md)).
Sign-in is Google or Discord. Stored identity is a provider ID and an email
address.

Planned personal data, and the rules it carries:

| Data | From | Rule |
|---|---|---|
| Provider ID, email | OAuth callback | Never rendered to another user |
| Display name, bio | Onboarding | Public to signed-in users |
| Avatar | R2 upload | Public to signed-in users, content-sniffed on upload |
| Birth year | Onboarding | Year only, never a full date. Displayed as an age band |
| Sex | Onboarding | Optional, with a "prefer not to say" value. Never inferred |
| Taste picks | Spotify search | Public to signed-in users |
| Conversation messages | Chat | Readable only by the two participants, ever |

The last row is the direct answer to the flaw in the app this replaces, which had
an endpoint returning every user's full record, message text included, to any
authenticated caller. Queries select the columns a screen needs and no more.

## Music data

Spotify is reached with Client Credentials, an app-level token with no user
context ([ADR 0006](adr/0006-declared-taste-over-listening-history.md)). The app
holds no Spotify user tokens and can read nobody's listening history. Similarity
is computed over artists and tracks a person picked deliberately, and the genre
vectors those picks imply.

## Security posture

In place now:

| Concern | Approach |
|---|---|
| Passwords | None stored, none accepted |
| Response headers | Set at the edge entry, asserted by `pnpm run budget` |
| Server bundle | Not reachable over HTTP |
| Input validation | Zod at every boundary |
| Third-party requests | None. Fonts self-hosted, provider marks inline SVG |
| Sign-in initiation | `POST`, so a prefetch or link scanner cannot start it |

Deferred, with the stage that closes each:

| Gap | Stage |
|---|---|
| Session cookies, CSRF tokens | 2 |
| Upload size limits and content sniffing | 4 |
| Rate limiting | 7 for vibrations, 9 globally |
| Content Security Policy | 9 |
| Data export and account deletion | 9 |
| Blocking and reporting | 9 |

CSP is deferred rather than forgotten. React Router inlines hydration state in a
`<script>` tag, so a useful policy needs per-response nonces threaded through the
document. That is worth doing once, properly, alongside the rest of the hardening.

## Why there is no API layer

Loaders and actions are the API. A route's loader reads, its action writes, and
both run on the same edge isolate as the renderer. Adding a REST layer in front
would mean a second set of schemas, a second auth check and a second place for
them to disagree. If a public API is ever wanted, it becomes a route module that
returns JSON from the same `app/lib/` functions the pages already use.
